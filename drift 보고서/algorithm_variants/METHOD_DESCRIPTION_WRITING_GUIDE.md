# 탐지 방법 설명 작성 가이드

이 문서는 `algorithm_variants/*_algorithm_variants.md`의 `## 변종:` 섹션을 사람이 읽는 설명으로 바꾸기 위한 기준이다. 목적은 DSL 노트를 그대로 보여주는 것이 아니라, 사용자가 탐지 방법의 의미와 결과 해석 방식을 이해하도록 돕는 것이다.

## 기본 원칙

각 변종 설명은 다음 질문에 답해야 한다.

1. 이 변종은 무엇을 감시하는가?
2. 어떤 데이터나 운영 상황에서 쓰는가?
3. 출력값은 무엇을 의미하는가?
4. 결과를 drift 후보로 어떻게 해석해야 하는가?
5. 어떤 조건에서는 결론을 조심해야 하는가?
6. 보고서에는 어떤 문장으로 쓰는 것이 적절한가?

## 권장 구성

각 `## 변종:` 섹션은 다음 흐름을 따른다.

1. 첫 문단: 변종의 핵심 의미를 2~4문장으로 설명한다.
2. 사용 상황: 이 변종이 적합한 입력 데이터, monitoring 목적, 운영 조건을 bullet로 적는다.
3. 해석 방법: statistic, distance, p-value, alarm, window, score 등 출력값을 어떻게 읽는지 설명한다.
4. 주의점: 검정 가정, sample size, threshold, label 지연, 원인 확정 불가 등 오해하기 쉬운 부분을 분리한다.
5. 보고서 문장 예시: 실제 보고서에 넣을 수 있는 3~5줄 문장을 제공한다.

## 작성 규칙

- `algorithmVariant`, `belongsTo`, `useWhen` 같은 DSL 블록만 남기지 않는다.
- method family 전체 설명을 반복하지 말고, 선택된 변종의 차이를 설명한다.
- "drift가 발생했다"고 단정하지 말고, 근거가 detector 출력뿐이면 "drift 후보", "분포 변화 신호", "성능 변화 신호"로 표현한다.
- p-value가 있는 검정은 "효과 크기"와 "통계적 유의성"을 구분한다.
- distance 계열은 distance 값이 커졌다는 사실과 원인 해석을 구분한다.
- classifier 기반 drift는 domain classifier가 두 분포를 구분했다는 뜻이지, 업무 원인이 확정됐다는 뜻이 아님을 적는다.
- supervised detector는 label 지연, class imbalance, error stream 정의를 반드시 언급한다.
- streaming detector는 alarm 시점, warning 상태, window 변화가 무엇을 의미하는지 설명한다.
- threshold는 운영 정책 또는 calibration 결과로 해석하고, 보편적 절대 기준처럼 쓰지 않는다.

## 보고서 문장 예시 형식

```text
[입력 신호]를 [변종명]으로 모니터링한 결과,
[주요 출력값]이 [기준 구간/threshold/과거 window] 대비 [변화 방향]을 보였다.
이는 [해석 가능한 drift 후보 신호]로 볼 수 있다.
다만 [주의 조건] 때문에 원인 또는 운영 영향은 [추가 확인 방법]으로 확인해야 한다.
```

## 검토 체크리스트

- 첫 문단만 읽어도 이 변종이 무엇을 하는지 알 수 있는가?
- 출력값 이름이 적어도 한 번 이상 자연어로 해석되어 있는가?
- "언제 쓰는지"와 "언제 조심해야 하는지"가 분리되어 있는가?
- 기존 DSL 노트보다 사용자가 읽기 쉬운 설명이 되었는가?
- 보고서 문장 예시가 실제 차트/DB 설명에 재사용 가능한가?
